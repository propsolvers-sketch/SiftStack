<objective>
Make `datasift_api.find_property_uuid_by_address()` survive street-suffix spelling
differences between our source portals and DataSift's stored records, without ever
guessing when the normalization is ambiguous.

Purpose: `_property_index_key()` is an exact lowercase string match. The T&B trustee
portal publishes `807 Briarwood Drive`; DataSift stores `807 Briarwood Dr`. The keys
`"807 briarwood drive|35022"` and `"807 briarwood dr|35022"` differ, so the lookup
returns None. Live evidence from GHA run 33728416332:

    no DataSift match for 807 Briarwood Dr (subtype=foreclosure_cancelled)
    no DataSift match for 807 Briarwood Dr (35022)

The `foreclosure_cancelled` tag never landed, so the operator cannot filter those
records — the subtype reached Notes only, and DataSift cannot filter on note text.
Four callers share this lookup and all four are silently degraded:
`scripts/apply_subtype_tags.py:75`, `scripts/apply_courthouse_snapshots.py:107`,
`scripts/capture_today_probate_uuids.py:59`, `scripts/capture_today_standard_uuids.py:72`.
The third one matters most: an empty `output/observability/today_probate_uuids.json`
forces `scripts/probate_cascade.py` off Path A onto a list query that (since 5146489,
2026-09-02) walks 8 DataSift lists instead of 3 — the suspected cause of the 5-hour
SmartSkip step on 2026-09-03.

Output: a shared zero-dependency suffix module, a second normalized index built in the
SAME pagination pass, an ambiguity guard that returns None on collision, a greppable
fallback-hit log line, and an offline regression suite.
</objective>
